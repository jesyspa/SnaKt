# F6 — Existential Quantifiers (`exists<T>`): Final Review

This feature adds an existential quantifier to SnaKt's specification DSL, the
dual of the existing `forAll<T>`. It lets a spec assert that *some* value
satisfies a predicate — the natural way to state that a search succeeds, that a
computed extremum is actually attained, or that a duplicate exists. This report
covers what shipped, what it unlocks, where its edges are, and how to use it.

Branch: `feature/f6-exists`. Grounded in the implementation diff
(`origin/main...feature/f6-exists`), the consolidated solver feedback
(`pipeline/f6-feedback.md`), the run log (`pipeline/runs/f6.md`), the Step 6
comparator verdict, and three independent solver runs against VerifyThis
problems.

---

## 1. What was implemented

### API surface

A single new builtin in the annotations module
(`formver.annotations/.../plugin/Builtins.kt`):

```kotlin
fun <T> exists(body: InvariantBuilder.(T) -> Unit): Boolean =
    throw FormverFunctionCalledInRuntimeException("exists")
```

A user writes `exists<T> { x -> <predicate over x> }` inside any specification
context — `preconditions`, `postconditions`, `loopInvariants`. The type argument
`T` names the domain the bound variable ranges over (`Int`, `Char`, …); the
lambda body is the predicate. Like `forAll`, it exists only to be read by the
plugin — calling it at runtime throws. It returns `Boolean`, so it composes with
`&&`, `||`, and `implies`, and can be nested inside or alongside `forAll`
(`exists { … exists { … } }`, `forAll { … implies exists { … } }`).

### Lowering to a Viper existential

The call is recognised as a special function in
`SpecialKotlinFunctions` (`FullySpecialKotlinFunction.kt`): the lambda argument
is destructured, and `StmtConversionContext.insertExistsFunctionCall` builds the
embedding. It allocates a fresh anonymous variable for the bound variable,
substitutes it into the lambda body via an inline method context, and collects
the body's conjuncts and any trigger expressions into an `ExistsEmbedding`
(`embeddings/expression/ExistsEmbedding.kt`) — a boolean-typed expression node
holding the bound variable, its conditions, and its triggers.

`LinearizationVisitor.visitExistsEmbedding` emits a Viper `Exp.Exists`. The
crucial contrast with `forAll` is the connective between the domain guard and the
body:

- `forAll` emits `∀ x :: guard ⇒ body` (`Exp.Implies`).
- `exists` emits `∃ x :: guard ∧ body` (`Exp.And`).

That is the correct existential shape: for a reference-typed bound variable the
guard is a runtime-type check (`x.isOf(...)`); for `Char` it is the code-point
range bound (below); otherwise there is no guard and the body stands alone. The
node also carries source position and source-role info for diagnostics, and
`exists` is registered as a reserved Viper keyword (`ViperKeyword.kt`), marked
pure in `ExpPurityVisitor`, and given a visitor hook in `ExpVisitor`.

### Two debug fixes

**Fix 1 — crash → graceful verification error** (`viper/.../ast/Info.kt`).
`Info.fromSilver` previously had `else -> TODO("Unreachable")`. Silicon can
attach its own info kinds (e.g. auto-generated trigger metadata) to the nodes it
reports errors on; when the error-reporting path hit such a node it raised
`kotlin.NotImplementedError: An operation is not implemented: Unreachable` and
failed the whole build. Those info kinds carry no SnaKt source role, so the
branch now returns `NoInfo`, letting the failure surface as an ordinary Viper
verification error. This was the single highest-leverage fix: the opaque crash
had caused one solver to spuriously abandon two problems that are in fact
verifiable, and it made every other `exists` failure undebuggable.

**Fix 2 — `Char` quantifier domain bound** (`LinearizationVisitor.kt`).
A `Char` bound variable is lowered to a Viper `Int`, so without a constraint it
ranges over *every* integer, including negative code points — and a claim true
for every real `Char` would fail on entry. A new `charDomainBoundOrNull()`
helper emits `0 <= x && x < 65536` (the Unicode code-point range) for
non-nullable `Char` variables, applied to both `forAll<Char>` and `exists<Char>`.
Users no longer need a manual `' ' <= c` guard.

### Regression tests

Three testData files under
`testData/diagnostics/verification/user_invariants/`:

- `exists.kt` — the positive case: `maxCharacter` verifies both a `forAll`
  upper-bound clause and an `exists` witness clause, with a witness-carrying loop
  invariant (see §4).
- `exists_char_bound.kt` — pins Fix 2: `forAll<Char>` over the emitted bound
  verifies; a bare untriggered `exists<Char>` is recorded as the known
  verification-error case (the instantiation gap of §3).
- `exists_double_index.kt` — pins Fix 1: the double-index existential that used
  to crash now degrades to a normal Viper verification error.

The generated golden list (`PhasedDiagnosticTestGenerated.java`) registers the
new tests.

## 2. Pros / what it unlocks

`exists` makes a class of proof obligations expressible that `forAll` alone
cannot state — anything of the form "there is a witness":

- **Extremum-with-witness.** "`m` is the maximum *and is attained*" needs
  `forAll { s[it] <= m } && exists { s[it] == m }`. The `forAll` half alone
  cannot say the maximum actually occurs in the sequence. (Verified:
  `maxCharacter` in `exists.kt`; `maxElim` from solver B.)
- **Duplicate / pair existence.** "The returned value occurs at two distinct
  positions" is a nested existential `exists i. exists j. i<j ∧ s[i]==v ∧ s[j]==v`.
  (Verified: TwoEq `findDuplicateValue` from solver A.)
- **Occupancy / membership checks, in both directions.** "Is any element in
  range `[lo,hi)`?" is a direct existential, and it verifies as an *iff*
  (`res == exists { … }`) with both directions auto-triggered when the bound
  variable indexes at the top level. (Verified: Downsampling `hasPointInVoxel`
  core from solver B.)
- **Constructive postconditions.** A search or extraction routine can now state
  that its result is genuinely witnessed by the input, not merely bounded.

Problems moved from blocked to verified by this feature (Step 6 comparator, no
regression on any):

- **2011 TwoEq** — duplicate-existence via nested `exists`/`forAll` with a
  witness-carrying invariant.
- **2011 MaxElim** — maximal-element index via search-by-elimination, scalar
  shadow witness plus invariant mirroring the postcondition.
- **2022 Downsampling (occupancy core)** — voxel-occupancy `exists`, verified as
  an iff at reduced (1D-integer) scope.

Nested `exists`/`forAll` translate and verify — `exists.exists`,
`forAll ⇒ exists`, and `exists` in loop-invariant position beside `forAll`
maximality clauses all work. Net solver outcome: 3 verified, 1 near-miss
(Minimum Excludant), 1 partial (Relaxed Prefix), and the rest blocked by
adjacent, non-`exists` limitations (§3).

## 3. Cons / limitations

Honest and specific. `exists` itself translates soundly; most of the walls below
are in the surrounding spec surface, not in the quantifier.

- **`String`-only modelling; array/`List` element access is not pure.** SnaKt
  models `String.length` and `String` indexing as pure, so they may appear
  inside quantifiers. `IntArray`/`List` element access inside a quantifier
  raises `freshAnonVar is not supported in a pure context`. The current
  workaround throughout the solver solutions is to encode the sequence as a
  `String` and reason with pure equality/ordering on its `Char` elements. This
  is the single biggest practical constraint on what `exists` specs can address.
- **`Char`/`Int` arithmetic is unsupported in specs.** `Char + Int` lowers to an
  uninterpreted `addCharInt(...)` with no successor/code-point axiom, so
  `char(r+1)` is unrelated to `char(r)+1`; `Char.code`, `Char - Char`, and
  comparing `s[i].code` to an `Int` all fail as `freshAnonVar is not supported
  in a pure context`, and there is no `sum` primitive. This blocks Minimum
  Excludant's minimality induction step (a near-miss — its `exists` translates
  fine; only the arithmetic obligation fails) and hard-blocks Kadane
  (maximum-sum subarray), which needs element arithmetic to even state its
  postcondition. This is an adjacent capability, explicitly deferred to its own
  feature, not an `exists` defect.
- **Split-point / boundary-variable `exists` won't instantiate (§4.2, deferred).**
  When the bound variable of an `exists` appears only as a *bound* feeding nested
  `forAll`s — `exists k. (forAll j. P) && (forAll j. Q)`, with `k` never a direct
  top-level index — Silicon gets no trigger and no ground term to instantiate the
  witness, even when it is trivially true (vacuous ranges). Solver B exhausted
  the manual rescues on Relaxed Prefix (bare invariant, trigger-anchor conjunct,
  planted ground terms) and none worked. The DSL currently exposes no witness or
  trigger hint (no Dafny-style `witness w`), so this pattern — common in relaxed
  matching, RLE, partitioning — yields only a partial verification. Deferred
  under F6: triggers cannot supply a ground witness, and a witness-hint DSL
  construct is out of scope.
- **A bare existential postcondition needs its witness carried by a loop
  invariant.** `exists` states *that* a witness exists but supplies no term for
  it. To verify an `exists` postcondition, the loop must carry the same
  quantified shape (bounded by the loop's progress variable) as an invariant, so
  the witness is propagated forward to the postcondition. This is the reliable
  idiom (§4), not a bug, but it is a real authoring burden — the spec must be
  designed around witness propagation.
- **A bare untriggered `exists<Char>` does not verify.** Even with the new
  `[0,65536)` bound emitted, a bare `exists<Char> { c -> c == ' ' }` is not
  instantiated by Silicon (no trigger, no ground witness) and reports a
  verification error — a specific instance of the instantiation gap above,
  pinned by `exists_char_bound.kt`.

## 4. Usage examples

All three snippets below verify against the built plugin.

### Maximum-with-witness (`exists.kt`, SnaKt testData)

The `forAll` clause says `m` is an upper bound; the `exists` clause says `m` is
actually attained. The loop invariant carries the witness forward.

```kotlin
fun maxCharacter(s: String): Char {
    preconditions { s.length > 0 }
    postconditions<Char> { m ->
        forAll<Int> { (0 <= it && it < s.length) implies (s[it] <= m) } &&
                exists<Int> { 0 <= it && it < s.length && s[it] == m }
    }

    var m = s[0]
    var i = 1
    while (i < s.length) {
        loopInvariants {
            1 <= i && i <= s.length
            forAll<Int> { (0 <= it && it < i) implies (s[it] <= m) }
            exists<Int> { 0 <= it && it < i && s[it] == m }   // witness carried forward
        }
        if (s[i] > m) { m = s[i] }
        i += 1
    }
    return m
}
```

### Duplicate existence, nested `exists` (2011 TwoEq, solver A)

The postcondition is a nested existential: two distinct positions both hold the
returned value. The invariant pair — a `forAll` ruling out early duplets plus an
`exists` asserting the known duplet still lies ahead — keeps the search
guaranteed to succeed.

```kotlin
@AlwaysVerify
fun findDuplicateValue(s: String): Char {
    preconditions {
        exists<Int> { i -> exists<Int> { j -> 0 <= i && i < j && j < s.length && s[i] == s[j] } }
    }
    postconditions<Char> { v ->
        exists<Int> { i -> exists<Int> { j -> 0 <= i && i < j && j < s.length && s[i] == v && s[j] == v } }
    }
    var i = 0
    while (i < s.length) {
        loopInvariants {
            0 <= i && i <= s.length
            forAll<Int> { a -> forAll<Int> { b -> (0 <= a && a < i && a < b && b < s.length) implies (s[a] != s[b]) } }
            exists<Int> { a -> exists<Int> { b -> i <= a && a < b && b < s.length && s[a] == s[b] } }
        }
        var j = i + 1
        while (j < s.length) {
            loopInvariants {
                i < j && j <= s.length
                0 <= i && i < s.length
                forAll<Int> { b -> (i < b && b < j) implies (s[i] != s[b]) }
                exists<Int> { a -> exists<Int> { b -> i <= a && a < b && b < s.length && s[a] == s[b] } }
            }
            if (s[i] == s[j]) { return s[i] }
            j = j + 1
        }
        i = i + 1
    }
    return s[0]  // unreachable: the carried existential contradicts i == s.length
}
```

### Occupancy as an iff (2022 Downsampling core, solver B)

`res` is proved *equivalent* to "some element lies in `[lo, hi)`". Because the
bound variable indexes at the top level, both directions of the iff
auto-trigger; the invariant mirrors the postcondition bounded by `i`.

```kotlin
@AlwaysVerify
fun hasPointInVoxel(p: String, lo: Char, hi: Char): Boolean {
    preconditions { lo <= hi }
    postconditions<Boolean> { res ->
        res == exists<Int> { i -> 0 <= i && i < p.length && lo <= p[i] && p[i] < hi }
    }
    var i = 0
    var found = false
    while (i < p.length && !found) {
        loopInvariants {
            0 <= i
            i <= p.length
            found == exists<Int> { j -> 0 <= j && j < i && lo <= p[j] && p[j] < hi }
        }
        if (lo <= p[i] && p[i] < hi) { found = true }
        i = i + 1
    }
    return found
}
```

## Summary

`exists<T>` is a sound, focused addition: it emits a genuine Viper existential
(`∃ x :: guard ∧ body`), composes with `forAll` and nesting, and verifies real
witness-bearing searches — maximum-with-witness, duplicate existence, occupancy
iffs — provided the sequence is `String`-encoded and the witness is carried by a
loop invariant. Two debug fixes harden it: the `Info.fromSilver` crash is now a
graceful verification error, and `Char` quantifiers get an automatic
`[0, 65536)` bound. Its limits are honest and mostly adjacent to the quantifier
itself: no pure element access on arrays/`List`, no `Char`/`Int` arithmetic in
specs, no witness-hint for the split-point/boundary pattern (deferred), and a
bare untriggered existential needs a ground witness to instantiate.
